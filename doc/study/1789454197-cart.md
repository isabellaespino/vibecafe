# Feasibility Study — Cart

## 1. Request

- A logged-in user can add a product to their cart, with a quantity, from
  the product detail page.
- A cart page lists the user's cart contents (product, quantity, and a
  total).
- Anyone not logged in is sent to a login page.
- Checkout and order history stay deferred.

## 2. Current state

- `products` app: `Product` (`name`, `price`), public list (`/`) and detail
  (`/product/<id>/`) pages.
- No `cart` app, no `CartItem` model.
- No customer-facing auth surface at all — `django.contrib.auth` is
  installed (it's a dependency of `django.contrib.admin`) but the only
  login page that exists is `/admin/login/`. No `registration/login.html`,
  no top-level `templates/` directory, no `LOGIN_URL` override (still
  Django's default `/accounts/login/`).
- `django.contrib.messages` is installed (ships with `startproject`) but
  unused by any template so far.

**Verdict:** feasible as a straightforward addition. The interesting
decisions are the same ones the original feasibility study flagged for
cart (§4.3, §5.2, §5.6, §5.8 of
`doc/study/1789410787-digital-cafe-feasibility.md`) plus one new one this
project didn't have yet: where the customer-facing login page and its
template live.

## 3. New app: `cart`

A new app, `cart`, owning `CartItem`, the add-to-cart view, and the cart
page view — mirrors how `products` owns `Product`. Folding `CartItem` into
`products` would couple an unrelated model (user-scoped, mutable) into an
app that's otherwise a plain read-only catalog.

## 4. `CartItem` model

```python
class CartItem(models.Model):
    user = models.ForeignKey(User, on_delete=models.CASCADE)
    product = models.ForeignKey(Product, on_delete=models.CASCADE)
    quantity = models.PositiveIntegerField()

    class Meta:
        constraints = [
            models.UniqueConstraint(fields=["user", "product"], name="unique_cart_item_per_user_product")
        ]
```

- No `added_at` timestamp — nothing in the request needs an insertion
  order; the cart page can order by product name (consistent with the
  homepage's existing ordering) instead of adding a field to sort by. Kept
  out per the same minimalism this codebase has applied to `Product`
  (no `description`/`is_active` until something needs them).
- `on_delete=CASCADE` on `product` (not `PROTECT`): a cart is not a
  historical record — this project's original feasibility study (§5.4)
  draws exactly this line, `PROTECT` for `OrderItem`, `CASCADE` for
  `CartItem`, because silently dropping a deleted product from an active
  cart is fine, but silently deleting order history is not. Order history
  is still deferred, so this doesn't come up yet regardless.
- `UniqueConstraint` (not the older `unique_together`) — one row per
  (user, product); "add to cart" for a product already in the cart
  increments `quantity` rather than creating a duplicate row. This is what
  makes "quantity" meaningful without also building a separate
  edit/remove UI (deferred — see §8).

## 5. Add-to-cart flow

### 5.1 Form + validation

A small `AddToCartForm(forms.Form)` with `quantity =
forms.IntegerField(min_value=1)` — rejects zero/negative/non-integer input
server-side (the HTML `<input type="number" min="1">` on the product
detail page is a UX nicety, not the enforcement boundary).

### 5.2 View

`POST /cart/add/<int:product_id>/`, `@login_required`, `@require_POST`.
On valid input: get-or-create the `CartItem` for `(request.user,
product)`; if it already existed, increment `quantity` via an `F()`
expression update rather than a Python read-modify-write:

```python
item, created = CartItem.objects.get_or_create(
    user=request.user, product=product, defaults={"quantity": form.cleaned_data["quantity"]}
)
if not created:
    CartItem.objects.filter(pk=item.pk).update(quantity=F("quantity") + form.cleaned_data["quantity"])
```

This matches the original study's §5.8 recommendation: closes the
double-submit race (double click, two tabs) at the SQL level instead of a
Python get-then-save round trip. `get_or_create` itself is already
race-safe against the create step, since Django wraps it in an atomic
block and the `UniqueConstraint` backs it.

On invalid input (e.g. quantity 0): redirect back to the product detail
page with a one-line error via `django.contrib.messages` — already
installed, zero new dependencies, just needs a `{% if messages %}` block
added to the product detail template.

On success: redirect to `/cart/`. (Landing on the cart page after adding —
rather than back on the product page — matches the request's framing that
the cart page is where quantities and the total are seen.)

### 5.3 Anonymous submission caveat — worth stating plainly

`@login_required` on a POST-only view has a real, known limitation: an
anonymous POST to `/cart/add/<id>/` gets redirected (302) to
`/accounts/login/?next=/cart/add/<id>/`. After a successful login, Django's
`LoginView` redirects to `next`, but the browser follows that redirect with
**GET**, not the original POST — and `/cart/add/<id>/` only accepts POST,
so this second request gets a clean `405`, not silently completed.

This means: logging in does not auto-complete the add-to-cart action that
triggered the redirect. The user is simply on the login page as requested,
and after logging in needs to go back to the product page and click "add
to cart" again. Building resume-after-login (stash the intended action in
session, replay it post-login) is real complexity for something the
request doesn't ask for — the request says anonymous users are "sent to a
login page," not "their action is retried after login." The original
study's §5.6 made the same call for the same reason (deferring a
session-based anonymous-cart-merge as unnecessary complexity given
accounts are admin-provisioned and scarce).

**Recommendation:** accept the 405-after-redirect behavior, verify it's a
clean 405 (not a 500) during manual testing, and don't build around it
unless asked.

## 6. Cart page

`GET /cart/`, `@login_required`, lists `CartItem.objects.filter(user=
request.user).select_related("product").order_by("product__name")`.

Per-item subtotal (`quantity * product.price`) and the cart-wide total are
both needed. Computing the total via `aggregate()` at the query level
avoids an N+1 read and matches the original study's pattern for `Order`
totals (§5.5 — compute on read, don't store a denormalized column that can
drift):

```python
items.aggregate(total=Sum(F("quantity") * F("product__price")))["total"]
```

Per-item subtotal still needs a value per row for display — simplest is a
`subtotal` property on `CartItem` (`self.quantity * self.product.price`),
called with no args from the template.

Currency rendering reuses the existing `₱{{ value|intcomma }}` pattern
(established in `doc/wiki/overview.md`, "Currency display") for both the
subtotal and total.

## 7. Login page

### 7.1 Why this needs a decision, not just a URL

Nothing customer-facing has needed auth before now. Wiring
`django.contrib.auth.views.LoginView` is one line, but it needs a
template, and unlike `products`, there's no natural app to own
`registration/login.html` (Django's default template name/path for
`LoginView`) — it's not `cart`-specific either; a future page could also
require login.

**Decision:** add a project-level `templates/` directory
(`BASE_DIR / "templates"`), added to `TEMPLATES[0]["DIRS"]`, holding
`registration/login.html`. This is the conventional Django place for
cross-app templates that don't belong to any single app's data model.

### 7.2 Wiring

- `LOGIN_URL = "login"` in settings, so `@login_required`'s redirect (and
  any future `LoginRequiredMixin`) resolves the right URL by name instead
  of hardcoding a path.
- `path("accounts/login/", auth_views.LoginView.as_view(template_name="registration/login.html"), name="login")`
  in `vibecafe/urls.py` (not `include("django.contrib.auth.urls")` — that
  bundle also wires password-reset and password-change views, which need
  their own templates and (for password reset) an email backend; none of
  that is in scope, and wiring it half-done would leave broken links/500s
  reachable at guessable URLs).
- No logout view. Not requested, and `/admin/logout/` already exists as an
  escape hatch for manual testing (the admin app is already installed).
  Flagged here explicitly as a deferred, not forgotten, decision.
- No self-registration — unchanged from the original study; accounts stay
  admin-provisioned via `/admin/auth/user/add/`.

## 8. Explicitly out of scope for this pass

- Removing an item from the cart, or editing its quantity after the fact.
  Not requested — the request describes "add" and "view," not "edit."
  Flagging this because a cart with no way to reduce/remove is a real UX
  gap a user will hit immediately; it's deferred deliberately, not an
  oversight, and should be the natural next study once checkout is picked
  back up (removing a line item is checkout-adjacent territory anyway).
- Checkout, `Order`/`OrderItem`, order history — per the request.
- Logout, password reset/change, self-registration.
- Session-based anonymous cart (§5.3) — anonymous users are redirected to
  login and that's it.

## 9. Feasibility verdict

Fully feasible, same shape as the previous two passes: one new small app
(`cart`), one new model, two new views behind `@login_required`, one new
project-level template for login, and a settings change (`LOGIN_URL`,
`TEMPLATES DIRS`, `INSTALLED_APPS` addition for `cart`). No new external
dependency — `django.contrib.auth` and `django.contrib.messages` already
ship with the project. The one real caveat worth carrying into the plan is
§5.3 (login redirect doesn't replay the POST) — it's correct Django
behavior, not a bug, but should be verified explicitly rather than assumed.
